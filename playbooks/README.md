# Development playbooks

A skill explains a bounded method. A playbook orders the work and gates. One agent executes the chosen playbook sequentially, including a distinct verification pass; no delegates, model comparison or background orchestration is required. Playbooks do not replace skills or change a planning-only request into implementation authorization.

Choose only the relevant procedure: [project development](project-development.md), [feature development](feature-development.md), [bug fix](bug-fix.md) or [refactoring](refactoring.md). Read its linked [gates](gates.md). Keep persistent working rules in the target's applicable instructions; these documents describe execution and assessment. Each existing skill remains independently usable without these playbooks.

For target use, copy this directory with its relative links intact to a chosen documentation location, or provide an accessible source path. It is plain Markdown, not an automatically discovered skill or slash command. Record its location in existing navigation. Skills are optional method providers: install only those needed as complete folders. If unavailable, perform the steps using target instructions and the gate criteria; do not create broken links to absent installations. Playbooks never require sibling skills at runtime, and skills never require playbooks.

Keep related work in one session while its context is useful. Start a fresh session for a separate goal with the requirements and state relevant to that goal.

Use an existing tracker for scope, requirement links, tasks, decisions, blockers and evidence. A brief checklist/report suffices for small work. Long work keeps a current checkpoint there rather than a parallel state file. Resume from applicable instructions, checkpoint, relevant specification/tasks and Git changes; reconcile changed assumptions and stale verification before selecting an eligible task.
